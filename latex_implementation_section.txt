\section{Реализация интеллектуальной системы}
\label{sec:development}

\subsection{Выбор средств реализации}

\textbf{Языки программирования, фреймворки и библиотеки}

Основным языком программирования для реализации программного комплекса был выбран Python (версия 3.10+). Выбор обусловлен наличием обширной экосистемы для работы с искусственным интеллектом, машинным зрением и обработки аудио. 

В проекте используются следующие ключевые фреймворки и библиотеки:
\begin{itemize}
    \item \textbf{FastAPI (версия 0.110+)} и \textbf{Uvicorn} — для построения высокопроизводительного асинхронного серверного ядра (бэкенда).
    \item \textbf{PyQt6} — для разработки кроссплатформенного графического пользовательского интерфейса (оверлея).
    \item \textbf{google-generativeai} — для взаимодействия с мультимодальной большой языковой моделью Gemini 1.5 Flash.
    \item \textbf{dxcam} и \textbf{OpenCV (cv2)} — для высокоскоростного захвата экрана (Windows Desktop Duplication API) и предобработки изображений.
    \item \textbf{faster-whisper} — для локального и быстрого распознавания речи (STT).
    \item \textbf{Silero TTS (через PyTorch)} и \textbf{sounddevice} — для локального синтеза речи и воспроизведения аудио.
    \item \textbf{ChromaDB} — в качестве векторной базы данных для организации контекстной долговременной памяти ассистента.
    \item \textbf{pynput} — для глобального перехвата горячих клавиш (Push-to-Talk).
\end{itemize}

\textbf{Обоснование выбора средств}

Выбор \textbf{FastAPI} продиктован необходимостью неблокирующей обработки запросов. Поскольку захват экрана, транскрибация аудио и запросы к LLM являются ресурсоемкими операциями (I/O-bound и CPU-bound), использование асинхронного цикла событий (Event Loop) позволяет системе не зависать в ожидании ответа сети.

Для реализации интерфейса был выбран \textbf{PyQt6}. В отличие от веб-интерфейсов, PyQt позволяет создавать окна системного уровня с флагом \texttt{WA\_TranslucentBackground} (прозрачность) и \texttt{WindowTransparentForInput} (пропуск кликов мыши насквозь). Это критически важно для игрового ассистента, так как интерфейс (оверлей) не должен перехватывать управление игрой.

Интеграция локальных моделей \textbf{faster-whisper} и \textbf{Silero TTS} позволяет минимизировать сетевую задержку. Обработка аудио происходит непосредственно на устройстве пользователя, что значительно ускоряет реакцию системы по сравнению с использованием облачных STT/TTS сервисов. Использование паттерна Inversion of Control (IoC контейнер \texttt{ApplicationContainer}) обеспечивает легкую заменяемость компонентов и расширяемость системы в будущем.

\textbf{Реализация пользовательского интерфейса}

Графический интерфейс реализован в парадигме компонентной архитектуры с использованием визуального стиля Glassmorphism (эффект матового стекла). Для соблюдения принципа единственной ответственности (SRP) монолитное окно было разделено на модульные компоненты: \texttt{SettingsPanel}, \texttt{StatusPanel}, \texttt{HotkeyPanel}, \texttt{SubtitlesHUD} и \texttt{VisualizerHUD}.

Оверлей функционирует в двух режимах, переключение между которыми осуществляется глобальной горячей клавишей (F2):
\begin{enumerate}
    \item \textbf{Интерактивный режим (Interactive Mode):} Фон затемняется, активируется перехват ввода. Пользователь может изменять настройки (выбор характера ИИ, голоса, громкости) и свободно перемещать элементы HUD (субтитры и индикатор) по экрану с помощью технологии Drag-and-Drop.
    \item \textbf{Режим HUD (Head-Up Display):} Фон становится полностью прозрачным, панели настроек скрываются. Элементы интерфейса пропускают сквозь себя клики мыши (click-through), отображая только текст ответа ассистента и компактный индикатор статуса поверх игрового процесса.
\end{enumerate}

Связь интерфейса с ядром системы реализована через механизм HTTP Polling: оверлей циклически (раз в 500 мс) опрашивает бэкенд для обновления статуса и получения новых ответов от модели.

\subsection{Реализация программного интерфейса}

Взаимодействие компонентов системы организовано через REST API, предоставляемое сервером FastAPI. Основная логика обработки запросов инкапсулирована в классе \texttt{RequestPipeline}, который реализует паттерн Producer-Consumer с использованием потокобезопасной очереди \texttt{asyncio.Queue}.

\textbf{Ключевые эндпоинты API:}
\begin{itemize}
    \item \texttt{POST /api/start} / \texttt{/stop} — управление жизненным циклом фоновых сервисов захвата экрана и микрофона.
    \item \texttt{GET /api/status} — получение текущего состояния системы (IDLE, RECORDING, PROCESSING).
    \item \texttt{GET /api/latest\_response} — получение последнего сгенерированного ответа ИИ.
    \item \texttt{GET /api/settings} и \texttt{POST /api/settings} — синхронизация динамических настроек (характер, голос, громкость, видимость HUD).
\end{itemize}

Пример обмена данными при сохранении настроек (POST-запрос на \texttt{/api/settings}):
\begin{verbatim}
// Запрос от PyQt6 оверлея
{
  "persona": "toxic",
  "voice": "baya",
  "show_subtitles": true,
  "show_visualizer": false,
  "volume": 0.8
}

// Ответ бэкенда
{
  "status": "settings updated"
}
\end{verbatim}

При активации режима Push-to-Talk извлекается последний кадр игры (\texttt{dxcam}), распознанный текст пользователя объединяется с изображением, контекстом из \texttt{ChromaDB} и системным промптом (зависящим от выбранной Persona), после чего мультимодальный запрос отправляется в Gemini API.

\subsection{Тестирование интерфейса}

\textbf{Функциональное и интеграционное тестирование}

В процессе разработки было проведено модульное и интеграционное тестирование основных узлов системы. Проверялись следующие сценарии:
\begin{enumerate}
    \item \textbf{Сценарий взаимодействия (PTT):} Удержание клавиши (L\_CTRL) корректно инициирует запись микрофона. Отпускание клавиши корректно формирует запрос в очередь \texttt{Pipeline}, где изображение и текст успешно обрабатываются LLM, а результат параллельно отправляется в оверлей и модуль TTS.
    \item \textbf{Сценарий управления UI:} Проверка сохранения настроек. Смена характера (Persona) немедленно обновляет системный промпт LLM, а изменение уровня громкости (0.0 - 1.0) корректно отрабатывается модулем `sounddevice` при синтезе речи.
    \item \textbf{Обработка исключительных ситуаций:} В ходе рефакторинга были устранены "глухие" исключения (bare excepts). Внедрена строгая обработка \texttt{requests.exceptions.RequestException} при потере связи между оверлеем и бэкендом, что позволяет корректно переводить UI в статус "ОФФЛАЙН" без аварийного завершения работы приложения.
\end{enumerate}

\textbf{Оценка удобства и качества взаимодействия}

Соответствие требованиям usability достигается за счет неинвазивности интерфейса. Режим HUD гарантирует, что ИИ-помощник не перекрывает важные игровые элементы и не блокирует управление. Качество взаимодействия оценивается как высокое благодаря низким задержкам на этапах захвата экрана и STT, однако итоговая скорость ответа зависит от времени генерации токенов облачным API Gemini. Наличие пресетов (Personas), вынесенных в отдельный конфигурационный JSON-файл, обеспечивает высокую степень персонализации опыта без необходимости модификации исходного кода.

\subsection{Вывод по разделу реализации}

В рамках данного этапа был успешно реализован полнофункциональный прототип неинвазивного мультимодального игрового ассистента. 

Разравботанная система поддерживает:
\begin{itemize}
    \item Голосовой ввод с локальной расшифровкой.
    \item Визуальный анализ ситуации в реальном времени посредством быстрого захвата кадров.
    \item Формирование ответов с учетом долгосрочного контекста диалога.
    \item Вывод информации через настраиваемый графический оверлей и локальный синтез речи.
\end{itemize}

Текущим ограничением прототипа является использование синхронного метода генерации LLM (отсутствие стриминга) и механизма HTTP-поллинга, что вносит небольшую задержку перед началом воспроизведения ответа. В качестве возможных направлений доработки выделяется перевод транспортного слоя графического интерфейса на WebSockets и реализация потокового воспроизведения аудио (TTS Chunking). Интерфейс и ядро системы полностью интегрированы и готовы к демонстрации в режиме реальной работы.
